## 1. Executive Summary

**GhostTrace** is an evidence-grounded deletion forensic engine built to audit customer data deletion across distributed enterprise systems. In modern event-driven architectures, simply issuing an account deletion API call is insufficient: personal data frequently persists in read replicas, analytics pipelines, unstructured logs, support tickets, and secondary search indexes. Even worse, active synchronization connectors or permissive backup restore policies can resurrect "ghost" data long after an account was supposedly deleted.

GhostTrace solves this by combining:
1. **Deterministic Identity Resolution**: Tracking historical names, emails, phone numbers, and SHA-256 identity hashes across time-series audit logs.
2. **Multi-Modal Evidence Ingestion**: Auditing 94 evidence files across 5 distinct modalities (SQL database dumps, structured JSON snapshots, JSON-Lines and key-value observability logs, PDF attachments via `pypdf`, and admin console screenshots via Windows Native WinRT OCR).
3. **Temporal Point-in-Time State Reconstruction**: Enforcing strict temporal boundaries (`event_time <= audit_at` and `captured_at <= audit_at`) to observe true resource states without future data leakage.
4. **Policy Treatment & Remediation Planning**: Translating organizational rules (`deletion_rules.csv`) into strictly ordered, evidence-backed findings, remediations, and verifications.

### 3.1 Fixture 1: Historical Identity Drift (`test_fixture_1_historical_identity_drift`)
* **Scenario:** A user requested deletion after changing their email address (`old.email` $\to$ `new.email`). The deletion worker deleted the primary account profile associated with the current email, but analytics telemetry retained an unanonymized record tied to the user's historical SHA-256 email hash (`44a65154...`).
* **Forensic Mechanism:** `IdentityResolver` resolves the user's historical audit trail (`user_audit_log.csv`) and indexes `all_email_hashes`. During log ingestion, the engine correlates the trace correlation key with the historical hash.
* **Result:** Successfully detected as `INCOMPLETE`. GhostTrace generated `FINDING` (`REPORT_EXPOSED_PII` on `analytics_platform`), followed by `REMEDIATION` (`ANONYMIZE_RECORD`) and `VERIFICATION` (`VERIFY_RECORD_ANONYMIZED`).

### 3.2 Fixture 2: Data Flow Re-creation Risk (`test_fixture_2_active_data_flow_risk`)
* **Scenario:** Primary account records were successfully erased, but a real-time CDC sync connector (`customer_events_connector` / `data_flow_1770`) in `integration_service` remained in state `enabled=true`. The active connector would repopulate downstream search and reporting databases upon any upstream webhook.
* **Forensic Mechanism:** The engine inspects observability logs (`resource_lookup_trace_*.log`) and extracts connector heartbeat and configuration events. Because `enabled=true`, GhostTrace identifies the active data flow risk under Rule 14.
* **Result:** Successfully classified as `INCOMPLETE`. Generated `REPORT_ACTIVE_DATA_FLOW` (state: `ACTIVE`), followed by `DISABLE_DATA_FLOW` (state: `DISABLED`) and verification `VERIFY_DATA_FLOW_DISABLED`.

### 3.3 Fixture 3: Policy-Mandated Account Tombstone Redaction (`test_fixture_3_policy_retained_redacted_tombstone`)
* **Scenario:** Under Rule 15, when an account is deleted, an internal `tombstone` record must be retained in `identity_service` to preserve referential integrity for statutory security audit logs (`Rule 12: RETAIN`). However, the tombstone must have all direct PII (names, emails, phone numbers) redacted.
* **Forensic Mechanism:** The engine verifies that the tombstone exists but contains null direct identifiers, confirming compliant retention.
* **Result:** GhostTrace generates `VERIFY_RECORD_REDACTED` with state `REDACTED` and evidence citation, successfully proving compliance without marking the case incomplete.

## 4. Key Architectural Discoveries & Engineering Decisions

1. **Two-Pass Log Stream Parsing & Trace Correlation:**
   - In raw log streams, request dispatch events (`*_started`) contain the search query (`lookup_key` or `subject_key`), while response events (`*_completed`) contain the observation (`resource_id`, `rows`, `http_status`, `enabled`).
   - *Decision:* Implemented a two-pass parser: Pass 1 links trace IDs to identity keys; Pass 2 ignores intermediate dispatch logs and evaluates only terminal completion events, preventing false "ABSENT" or "DISABLED" intermediate states.

2. **Primary Account Numbering vs. Concurrent Activity Race Conditions:**
   - In `system_activity.csv`, the deletion worker processes tasks for many users simultaneously. Filtering deletion worker activities by timestamp alone caused requests to erroneously attach to concurrent users' accounts.
   - *Discovery:* In Northstar Shop, user accounts follow strict deterministic identity mapping: `user_XX` maps directly to `account_0XX` (e.g. `user_01` $\to$ `account_001`, `user_8741` $\to$ `account_8741`).
   - *Decision:* GhostTrace prioritizes direct evidence observations, falling back to deterministic user-to-account mapping, eliminating concurrency misattributions.

3. **Multi-Modal Evidence Ingestion Without Heavy External Dependencies:**
   - Admin portal screenshots contain crucial readback confirmations. Rather than relying on heavyweight external OCR packages with fragile binary dependencies, GhostTrace leverages Windows Native Runtime OCR (`Windows.Media.Ocr` via `winocr`), enabling fast, deterministic, offline text extraction on Windows.

4. **Strict Temporal Point-in-Time Isolation:**
   - Forensic evidence captured after `audit_at` cannot be used to evaluate state as of `audit_at`. GhostTrace enforces hard filtering: all evidence files with `captured_at > audit_at` and log activities with `event_time > audit_at` are quarantined, ensuring zero future-data leakage.
